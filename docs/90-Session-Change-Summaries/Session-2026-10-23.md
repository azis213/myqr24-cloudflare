## 2. Kernaussagen aus `AGENT.md`

- **Projekt:** myQR24 Edge Tag Router – Cloudflare Worker (TypeScript), der öffentliche NFC-/QR-Tag-URLs auflöst, Tag-IDs decodiert, Range/Gruppe/Features aus Cloudflare KV ermittelt und Redirect oder JSON-Aktionsdokument zurückgibt.
- Der Worker ist **ausschließlich eine lesende Edge-Auflösungsschicht** – keine Fachlogik, keine personenbezogenen Daten.
- **Maßgebliche Dokumente vor Änderungen lesen:**
  - `docs/ARCHITECTURE.md`
  - `docs/DOMAIN_RULES.md`
  - `docs/10-Architecture/CLOUDFLARE_PWA_COMPONENT.md`
  - `docs/40-Implementation/STATUS.md` (Hinweis: der tatsächliche aktive Statusort ist `docs/40-Implementation/10-Implementation-Orchestration/STATUS.md`)
  - `docs/40-Implementation/20-TEST-STRATEGY.md` / `21-TEST-CASES.md`
  - `docs/90-Session-Change-Summaries/DEPLOYMENT_HANDOVER.md`
- **`docs/00-Refinement/**` ist unverbindlicher Ideenspeicher** – darf bei regulären Sessions NICHT gelesen oder als Anforderung interpretiert werden. Nur bei explizitem Refinement-Auftrag zulässig. Ideen müssen erst über Architektur/Contracts/Stories/Tests/Traceability/Status übernommen werden, bevor sie gültig sind.
- **Domainmodell (URLs):**
  | Umgebung | kurze Scan-URL | sprechende Scan-URL |
  |---|---|---|
  | Staging | `https://s.qx4.uk/{tagId}` | `https://s.myqr24.com/t/{tagId}` |
  | Produktion | `https://qx4.uk/{tagId}` | `https://p.myqr24.com/t/{tagId}` |
  - Verboten/nicht reaktivieren: `qx4u.uk`, `p.myqr24.net`, `t.qx4.uk`, `t.myqr24.com`.
- **Host-Sicherheitsregel:** Allowlist explizit in `src/index.ts`, umgebungsgetrennt (Staging: `s.qx4.uk`/`s.myqr24.com`; Production: `qx4.uk`/`p.myqr24.com`). Unbekannte Hosts/Pfade/Cross-Environment → fail-closed `404`. Keine Wildcards.
- **Umgebungstrennung:** eigene Worker, eigene `TAG_CONFIG`-KV-Namespaces, eigene versionierte Secrets pro Umgebung (`FEISTEL_SECRET_S01`, `TAG_HMAC_SECRET_S01`, `REDIRECT_SIGNING_SECRET_S01` für Staging). `SCAN_ENVIRONMENT` steuert Zuordnung in `wrangler.toml` (`staging` → `myqr24-edge-routing-staging`, `production` → `myqr24-edge-routing`). **Secrets niemals in Git/Docs/Tickets/Chat speichern.**
- **Tag-/KV-Regeln:**
  - Tag-ID-Längen: 6 oder 8 Base36-Zeichen.
  - Alle Zahlenwerte als `BigInt`, nie `number`.
  - Kanonischer Zahlenraum: `I(L) = [36^(L-1), 36^L)`.
  - 8-stellige IDs: HMAC-Nibble in unteren 4 Bit.
  - 8-stellige Ranges: vollständige 16er-Slots (`start % 16 === 0`, `end % 16 === 15`).
  - `tag-range-index` muss aufsteigend sortiert, nicht überlappend sein.
  - Feature-Priorität: `tag:{decodedValue}` vor `range-rule:{rangeId}` vor `group:{groupId}`.
  - Ohne gültige aktive Range: kein Tag auflösbar.
  - Fehlerhafte/unvollständige Konfiguration → fail-closed `404`.
- **Architekturgrenzen (NICHT im Edge Worker/Routing-KV):** Owner-/Besucher-Sessions, Chat, Lost&Found-Status, Gästebuch, Check-in/Standort/Collection/Campaign/Reward, private R2-Pfade, Berechtigungs-/Verwaltungslogik. Diese gehören in spätere PWA-/API-Komponenten mit D1/PostgreSQL, privaten R2-Buckets, ggf. Durable Objects.
- **Entwicklungsregeln:**
  1. Änderungen an URL-Formaten, Feistel-Parametern, HMAC, Ranges, Secrets sind sicherheitsrelevant → Architektur-/Test-/Doku-Updates nötig.
  2. Tests vor/nach Änderungen ausführen.
  3. Neue Regeln durch Vitest-Tests abdecken.
  4. Bei Architektur-/Statusänderungen passende `docs/`-Dateien aktualisieren.
  5. Neue Session-Übergaben in `docs/90-Session-Change-Summaries/` ablegen.
  6. Deployment-Nachweise in `docs/40-Implementation/evidence/`.
  7. Keine produktiven Tags, bevor Production-Worker/KV/Secrets/Routen verifiziert sind.
- **Qualitätsbefehle (vor Abschluss relevanter Änderungen):**
  ```sh
  npm test
  npx tsc --noEmit
  npx wrangler deploy --dry-run --outdir dist --env staging

  git diff --check
  ```

  Deployment-Reihenfolge: zuerst Staging (`npm run deploy -- --env staging`), Production erst nach dokumentierter Staging-Abnahme (`npm run deploy -- --env production`).
